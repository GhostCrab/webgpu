# Fix the solver before the grid

The simulation's integrator formula is correct and its WebGPU calls are all still current, but three defects in the solver matter more than anything the newer standard or a different grid structure would add. The timestep varies from frame to frame while the integrator assumes it is fixed, the default reflective boundary has a sign error that leaves particles outside the circle, and the four-pass collision scheme that the architecture document calls race-free is not: neighbouring invocations write the same particles. On the WebGPU side, nothing the code uses has been deprecated or removed; its age shows in what is missing (no device-loss handling, no visible failure path, no GPU timing) and in a render path that allocates roughly 300 MB of targets to draw flat additive discs. On "spatial hashing", the code does not hash at all. It uses a dense uniform grid with per-bin linked lists, which is a legitimate design, and a hash table is the wrong move for a fixed square domain. The grid's real cost is that it is 35 times larger than the particle count, is rebuilt 20 times a frame, and is dispatched per bin instead of per particle. Every finding about the local code comes from reading it at commit `505b00e`; nothing was run or profiled, so the costs below are counts of work, not timings, and the race is derived from the code, not observed.

## The integrator is textbook Verlet fed a timestep it was not designed for

The update in `src/verlet/shaders/integrate.wgsl:15-23` is plain position (Stormer) Verlet with a stored previous position: `pos = pos + (pos - prevPos) + accel * dt * dt`. That is the same scheme as Jakobsen's 2001 paper, and the collision response and substep order match the widely copied VerletSFML reference almost line for line ([Jakobsen](https://www.cs.cmu.edu/afs/cs/academic/class/15462-s13/www/lec_slides/Jakobsen.pdf), [VerletSFML](https://raw.githubusercontent.com/johnBuffer/VerletSFML/main/solver.hpp)). The formula is right, and the structure of 20 substeps with one collision sweep each is what the "Small Steps" paper recommends: n small steps with one solver iteration each beat one large step with n iterations, because position error from external forces scales with dt squared ([Macklin et al. 2019](https://mmacklin.com/smallsteps.pdf)).

The problem is the condition Jakobsen attaches to the formula: "keeping the time step fixed". The code derives `deltaTime` from `Date.now()` differences clamped to 1/60 s (`src/renderer.ts:125-132`, `src/verlet/verlet.ts:223-240`). `Date.now()` has millisecond resolution, so at 60 Hz the frame time alternates between 16 ms and 16.67 ms, and on a 144 Hz display between 6, 7 and 8 ms. Because the carried displacement `pos - prevPos` is not rescaled when dt changes, the simulation behaves like a fixed-step one whose **gravity fluctuates by about 8% frame to frame at 60 Hz** and far more on high-refresh displays. It also means the app runs a different simulation from the tests, which pass exact frame times. The standard remedy is a constant dt fed from an accumulator with a cap on steps per frame ([Fiedler](https://gafferongames.com/post/fix_your_timestep/)); the alternative, time-corrected Verlet, scales the carried displacement by dt(i)/dt(i-1) ([Wikipedia](https://en.wikipedia.org/wiki/Verlet_integration)). A fixed step is simpler and is the one to choose. Take the time from the `requestAnimationFrame` timestamp instead of `Date.now()`.

The second defect is in the default boundary. `classicConstrain` is false (`src/simulation-controls.ts:19`), so the reflective branch at `src/verlet/shaders/constrain.wgsl:32-50` runs. A hand calculation shows it fails: with the limit at 100, `prevPos = (99.5, 0)` and `pos = (100.5, 0)`, the code computes a bounce length of -0.5 and places the particle at (100.5, 0), exactly where it started and still outside. A geometric reflection gives 99.5. Two errors combine (a wrong sign, and a length multiplying an un-normalised vector), and the branch also reflects without checking whether the particle is already moving inward, ignores `constrainCenter`, and applies its 0.8 loss on every substep outside the boundary instead of once per impact. The repair is to place the particle on the boundary, take v = pos - prevPos, reflect only when dot(v, n) > 0 using v' = v - (1 + e) dot(v, n) n, and rebuild `prevPos` from v'. This also resolves the code's own noted issue that a large correction turns into a large inward velocity (`constrain.wgsl:22-23`). This analysis is a hand calculation; a one-particle harness test would confirm it.

What the code lacks relative to Position Based Dynamics and XPBD is an explicit velocity. PBD is "in exact correspondence" with a Verlet step but keeps velocity because that "allows for a more intuitive way of manipulating" it: restitution, friction and damping are applied in a velocity pass after the solve ([Muller et al. 2007](https://matthias-research.github.io/pages/publications/posBasedDyn.pdf)). Here every collision correction moves `pos` and not `prevPos` (`collide.wgsl:75,85`), so all of it becomes velocity on the next step. Both Small Steps and the Unified Particle Physics paper name this as the cause of "popping" and note it gets worse as the timestep shrinks; the fixes are a cap on depenetration speed or a pre-stabilisation pass ([Macklin et al. 2019](https://mmacklin.com/smallsteps.pdf), [Macklin et al. 2014](https://mmacklin.com/uppfrta_preprint.pdf)). The collision stiffness is also a bare multiplier (0.5 x 0.65 per visit, each pair visited twice, so about 54% of an overlap is removed per substep), which ties contact softness to the substep count. That is the PBD limitation XPBD was written to remove ([Macklin et al. 2016](https://matthias-research.github.io/pages/publications/XPBD.pdf)).

Two further numerical points follow from storing the previous position. First, there is no speed limit. Bins are one diameter (3 units) wide and free fall across the circle reaches about 3,570 units/s, roughly one full diameter per substep, so tunnelling and out-of-grid positions are reachable, more so with the click force at its 10,000 maximum. A clamp of about one radius per substep in `integrate.wgsl` fixes this; a much tighter version already sits commented out at `constrain.wgsl:54-59`. Second, velocity is recovered by subtracting two coordinates near 1,000, where a float32 step is about 1.2e-4. The per-substep gravity increment is 2.1e-3 units at 60 Hz (about 17 float steps) and 3.6e-4 at 144 Hz (3 to 6 steps), so gravity is coarsely quantised on fast displays and raising the substep count makes it quadratically worse. Small Steps names this limit directly ([Macklin et al. 2019](https://mmacklin.com/smallsteps.pdf)). Storing the per-substep displacement as its own field in place of `prevPos` removes the cancellation and gives the explicit velocity that restitution, friction and timestep changes need. This arithmetic is derived, not measured.

## The four-colour collide writes outside its own bin, so it races

Each `collide` invocation owns one bin at `2 * id + offset` and tests its particles against the 3x3 neighbourhood, writing the *other* particle's position immediately wherever it lives (`src/verlet/shaders/collide.wgsl:9-22,75`). Owners in one pass are two bins apart. The owner of column c writes columns c-1 to c+1; the owner of column c+2 writes c+1 to c+3. **Column c+1 is written by both in the same dispatch**, and a bin diagonal to four owners is written by all four. The writes are unsynchronised read-modify-writes, so corrections can be lost. WGSL makes avoiding such races the shader author's responsibility ([WGSL](https://www.w3.org/TR/WGSL/)). A write footprint of radius one needs owners three apart, which is nine colours, not four. `docs/architecture.md:54-56` therefore overstates the scheme, and `docs/testing.md:27` attributes irreproducibility to the binning atomics alone when there is a second source. Whether the race is visible, or absorbed by 20 substeps of relaxation, is unknown.

The literature offers two race-free options: a Jacobi solver or graph colouring ([Muller, Ten Minute Physics 16](https://matthias-research.github.io/pages/tenMinutePhysics/16-GPUSimulation.pdf)). The Jacobi form is the reference design for particle grids. Each particle reads neighbours from one buffer and writes only its own result to another; Green's CUDA sample double-buffers for this reason ([Green 2010](https://developer.download.nvidia.com/assets/cuda/files/particles.pdf)). Applied here, eight dispatches per substep become one or two, sized by particle count, with no `cso` buffer and no `collideIncrement` shader. The cost is convergence: Jacobi "is not guaranteed to converge" and propagates corrections only one particle per iteration, so it needs constraint averaging (divide each particle's summed correction by its contact count) with an over-relaxation factor between 1 and 2 ([Macklin et al. 2014](https://mmacklin.com/uppfrta_preprint.pdf)). Piles will look softer per substep; the 20 substeps offset that.

The alternatives keep the current Gauss-Seidel feel. Nine colours (stride 3) removes the race at 18 dispatches per substep. A cheaper variant is for each invocation to own a disjoint 2x2 block of bins and resolve only pairs inside it; the four existing offsets still cover every adjacent pair. That scheme is a construction from the colouring rule, not something found in a source, so it needs a test before trust. The choice between gather and colouring changes how stacks behave and cannot be settled without running both. My recommendation is the per-particle gather, because it also removes the empty-space cost described below.

Several smaller defects sit in the same shader. The same-bin shortcut compares a bin index to 4 where the neighbourhood slot was intended (`collide.wgsl:43-48`, issue #1), so every pair is resolved twice per substep and collisions with real bin 4 are skipped. Fixing it alone would make same-bin pairs resolve once and cross-bin pairs twice, so fix it together with the collide rewrite and re-measure baselines once. The 1000-test cap is counted per bin and never reset (`collide.wgsl:24-25,53-57`), so in a crowded bin the remaining particles stop colliding for that pass, and which ones depends on list order. Coincident particles and a particle exactly at the click point produce NaN (`collide.wgsl:65-66`, `apply-forces.wgsl:19-22`) with no guard.

## It is a dense grid, not a hash, and a hash would not help

The structure in `src/verlet/verlet-bin-computer.ts:121-125` and `src/verlet/shaders/bin-set.wgsl:12-22` is a bounded uniform grid: the bin index is the plain row-major cell index, each bin holds one head pointer, and each particle holds a `binLink` to the next, pushed lock-free with `atomicExchange`. There is no hash function and no table smaller than the grid, so the "spatial hash" heading in `docs/architecture.md:48` is a misnomer.

Spatial hashing in the sense the owner has heard about solves one problem. Muller's tutorial presents the dense grid first and substitutes `hash(xi, yi) % tableSize` specifically to "handle unbounded grid", keeping everything else the same ([Muller, Ten Minute Physics 11](https://matthias-research.github.io/pages/tenMinutePhysics/11-hashing.pdf)). The price is false-positive candidates from hash collisions and the loss of adjacency between neighbouring cells. This simulation is a fixed 2160-unit square, and the bounded WebGPU particle projects found all use a dense grid with clamped indices ([lisyarus](https://lisyarus.github.io/blog/posts/particle-life-simulation-in-browser-using-webgpu.html), [water-webgpu](https://github.com/piellardj/water-webgpu)). **Hashing becomes right only if the domain stops being a fixed square.** No measured hash-versus-dense GPU benchmark was found in any year, so this judgement is structural.

What current practice does differently is the list, not the index. The standard since Green (2010) and Hoetzlein (2014) is a counting-sort grid: count particles per cell with an atomic add, prefix-sum the counts, scatter particles into contiguous runs. Hoetzlein's version takes 4 kernel calls against 15 for a radix sort and ran 5 to 10 times more queries per second ([Hoetzlein 2014](https://ramakarl.com/pdfs/2014_Hoetzlein_Fast_Neighbors.pdf)). Green found the sorted path fastest on most hardware because it "improves the memory access coherency" ([Green 2010](https://developer.download.nvidia.com/assets/cuda/files/particles.pdf)). The 2025 and 2026 WebGPU projects re-implement exactly this in WGSL at 65 thousand to a million particles ([lisyarus](https://lisyarus.github.io/blog/posts/particle-life-simulation-in-browser-using-webgpu.html), [water-webgpu](https://github.com/piellardj/water-webgpu), [Pandora](https://pajouheshgar.github.io/blog/posts/pandora-artificial-life)). The newest research, ray-tracing-hardware search and compressed neighbour lists, targets large or varying radii and does not apply to one radius in a bounded 2D box ([arXiv 2601.15633](https://arxiv.org/abs/2601.15633), [arXiv 2602.19873](https://arxiv.org/abs/2602.19873)).

| Structure | Build | Neighbour read | Fits this simulation? |
|---|---|---|---|
| Dense grid, linked list (current) | clear + one atomic pass | pointer chase through 80-byte structs | Works; simplest build |
| Dense grid, counting sort | clear + count + scan + scatter | contiguous run per cell | The standard; worth it at 100k+ particles |
| Hash table, counting sort | same, on a table of about N entries | same, plus false positives | Only for an unbounded domain |
| Fixed slots per cell | clear + one atomic pass | K contiguous reads | No: drops particles under compression |
| BVH, ray-tracing structures | sort + tree build | stack traversal | No: one radius, no RT API in WebGPU |

The linked list is not the main cost here. The grid is. At bin side 3 the grid is 720 x 720, **518,400 bins for 15,000 particles**, so at least about 97% of bins are always empty. `bin-clear` writes all of them every substep (10.4 million writes a frame) and the four per-bin collide dispatches launch about 541,000 invocations per substep to service 15,000 particles. Both scale with domain area, not particle count. Per-particle collide dispatch removes the second cost outright. The first falls to the Small Steps pattern: detect collisions once per frame with a margin and reuse the result across substeps ([Macklin et al. 2019](https://mmacklin.com/smallsteps.pdf)). Here that means bins of a diameter plus a margin, rebuilt every k substeps, which is only safe once a speed limit bounds how far a particle moves between rebuilds.

Three small fixes to the build are independent of all that. `bin-set` does not clamp its coordinates, so a stray particle lands in the wrong row or indexes outside the buffer; clamping into edge bins is what lisyarus does. `bin-link-clear` is redundant: only invocation i writes particle i's link, so a plain store of the `atomicExchange` result suffices, which deletes one dispatch per substep, the `VerletObjectAtomicBin` struct and the test guarding it. And neighbour indices built by flat arithmetic wrap across rows at the left and right edges (`collide.wgsl:18-22`), costing wasted list walks.

A full counting sort with reordered particles is the standard end state but **is not worth its complexity at 15,000 particles**, where the whole particle buffer is 1.2 MB. With 518,400 bins the naive doubling prefix sum would need 20 sweeps per build, so it would also require a blocked scan. It becomes the dominant win if the target moves to hundreds of thousands of particles, and it costs stable particle indices, which the hand-computed tests rely on.

## Nothing in the WebGPU code is deprecated; the gaps are lifecycle, waste and measurement

The code uses only core WebGPU 1.0 with default features and limits (`src/renderer.ts:52-55`), and none of the removals since early 2025 touch it: `requestAdapterInfo()`, `maxInterStageShaderComponents`, `GPUAdapter.isFallbackAdapter` and `bgra8unorm` storage textures were all removed from Chrome and none is used here ([What's New in WebGPU](https://developer.chrome.com/docs/web-platform/webgpu/news)). The installed `@webgpu/types` is 0.1.74, the latest; only the `^0.1.26` range in `package.json` is stale. Structurally the code already does the right things: one submit per frame, pipelines and bind groups created once, one uniform write per frame.

Reach has grown substantially. Core WebGPU is now on by default in Chromium on Windows, macOS, ChromeOS, most Android 12+ devices and parts of Linux, in Safari 26 on all Apple platforms, and in Firefox on Windows (141) and Apple-silicon Macs; Firefox on Linux, Intel Macs and Android is still not on by default ([gpuweb Implementation Status](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status)). Because the app needs only core defaults it runs everywhere WebGPU does. What it does on the remaining platforms is nothing: a missing `navigator.gpu`, a null adapter and a rejected device all collapse into a silent `return false` (`src/renderer.ts:35-65`). There is also no `device.lost` handler and no `uncapturederror` listener, although the tests have both (`test/gpu.ts:17-20`). Best practice is to attach the loss handler immediately and, on loss, request a *new* adapter; since Chrome 140 an adapter is consumed by its first successful `requestDevice()` ([toji.dev](https://toji.dev/webgpu-best-practices/device-loss), [Chrome 140](https://developer.chrome.com/blog/new-in-webgpu-140)).

The render path is where the template origin shows. Particles are drawn into a 4x MSAA 3840x2160 colour target with a 4x MSAA depth-stencil attachment, then presented through a second MSAA pair (`src/simulation-target.ts:31-63,122-130,167-182`). The particle pipeline writes no depth and its compare always passes (`src/verlet/verlet-renderer.ts:54-78`), so the depth-stencil attachments do nothing. By arithmetic, the MSAA colour target alone is about 133 MB and the set is **roughly 300 MB of render targets**. Dropping both depth-stencil attachments, presenting single-sampled, and using `storeOp: 'discard'` on the MSAA colour target changes nothing visually.

Of the features added since early 2025, few earn a place here, and none should become a hard requirement.

| Feature | Status | Verdict for this code |
|---|---|---|
| `timestamp-query` in passes | Chrome 121, Safari 26, no Firefox | Adopt, optionally: it is the missing measurement tool |
| Transient attachments | Chrome 146 | Optional extra on the MSAA target, behind an `in` check |
| Immediates (`var<immediate>`) | Chrome 149-150 | Skip; core alternatives do the same job |
| Compatibility mode | Chrome 146, Android first | Optional reach to GLES 3.1 devices; needs device testing |
| Subgroups | Chrome 134, no Firefox | Skip; they coordinate within a workgroup, not across a dispatch |

Sources for the table: [Chrome 146](https://developer.chrome.com/blog/new-in-webgpu-146), [Chrome 149-150](https://developer.chrome.com/blog/new-in-webgpu-149-150), [Chrome 144](https://developer.chrome.com/blog/new-in-webgpu-144), [Chrome 147-148](https://developer.chrome.com/blog/new-in-webgpu-147-148), [Chrome 153-154](https://developer.chrome.com/blog/new-in-webgpu-153-154), [MDN browser-compat-data](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/GPUSupportedFeatures.json). The W3C specification text and Firefox and Safari release notes were not read, so support outside Chrome rests on the status wiki and MDN data, and which WGSL language extensions those browsers expose was not checked.

Immediates deserve one more sentence because they look tailor-made for the `collideIncrement` shader, which exists only to change two integers between dispatches and accounts for 80 of the frame's 280 dispatches. The same result is available in core WebGPU through a dynamic-offset uniform or four pre-built bind groups, and the per-particle gather removes the need entirely. Timestamp queries are the one new capability to adopt now, gated on `adapter.features.has('timestamp-query')`, because every performance claim in this report is a work count and no published figure for per-dispatch overhead in WebGPU was found.

## One ordered plan across all three questions

The three reviews converge on the same sequence, and the order matters because early items make later ones measurable. Value and effort are judgements from the code; none of these changes has been prototyped, and every behavioural change will move the measured baselines in the simulation tests, which need re-measuring as `docs/testing.md` describes.

| # | Change | Value | Effort |
|---|---|---|---|
| 1 | Fixed timestep from the rAF timestamp | High | Low |
| 2 | Repair the reflective constrain; rebuild `prevPos` from reflected velocity | High | Low |
| 3 | Clamp bin coordinates; guard zero-distance NaN; clamp speed to about one radius per substep | High | Low |
| 4 | Visible startup failure path, `uncapturederror` listener, device-loss recovery | High | Low to medium |
| 5 | Remove depth-stencil attachments and present-pass MSAA; discard the MSAA store | High | Low to medium |
| 6 | Optional `timestamp-query` profiling in the app and the test harness | Medium-high | Medium |
| 7 | Replace the four-pass collide with a per-particle gather plus averaging | High | Medium |
| 8 | Remove `bin-link-clear` and the atomic particle view; fold forces into integrate | Medium | Low |
| 9 | Rebuild the grid every k substeps with a bin margin | Medium | Small to medium |
| 10 | Store displacement instead of `prevPos`; compact the 80-byte particle to about 32 bytes | Medium | Medium |
| 11 | Counting-sort grid with reordered particles | High only at 100k+ particles | Large |

Items 1 to 3 come first because a jittering timestep and a boundary that leaves particles outside confuse any evaluation of the solver. Items 4 and 5 carry no risk to simulation behaviour and can land at any time. Item 6 precedes the performance work so that items 7 to 9 are judged on timings. Item 10 makes restitution, friction and wall losses explicit and is defensible earlier if the layout churn is acceptable; `particle-layout.ts` derives offsets from `common.wgsl`, which contains the change.

## Conclusion

The owner's three questions assumed the code had aged in its integrator, its API usage and its grid structure. The reading reverses that picture: the formula, the API calls and the choice of a dense grid all hold up, and the weaknesses are in the joins between them. The timestep feeding the integrator, the write footprint of the collide shader relative to its colouring, and the ratio of grid size to particle count are each a place where a sound component is used outside the condition that makes it sound. That is why the highest-value fixes are small and none needs a new WebGPU feature.

The decision that remains open is physical, not technical. A per-particle Jacobi gather and a correctly coloured Gauss-Seidel pass are both race-free, but they stack and settle differently, and the literature's convergence warnings come from other simulations. Running both behind a fixed timestep, with timestamp queries in place, is the experiment that settles it. The same instrumentation will show whether 20 substeps are still needed once the solver is race-free and speed-limited. If they are not, cutting the substep count would save more work than any change to the grid.
